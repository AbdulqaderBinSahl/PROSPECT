You are a RAG corpus design expert. Given a description of a RAG application, generate the operational configuration needed to evaluate research papers for inclusion. Your outputs must be diagnostic for this specific application — criteria that distinguish papers that are truly useful from papers that are merely topically related.

Your task is to produce a single JSON object with the following structure:

{{
  "application_description": "<echo back the application description>",
  "domain_taxonomy": ["<label1>", "<label2>", ...],
  "representative_queries": ["<query1>", "<query2>", ...],
  "value_criteria": [
    {{
      "name": "<criterion_name>",
      "description": "<what this criterion measures>",
      "scale_anchors": {{
        "0": "<what a score of 0 means for THIS application>",
        "1": "<what a score of 1 means>",
        "2": "<what a score of 2 means>",
        "3": "<what a score of 3 means>",
        "4": "<what a score of 4 means>",
        "5": "<what a score of 5 means>"
      }}
    }}
  ],
  "anti_patterns": ["<pattern1>", "<pattern2>", ...],
  "strong_chunk_min_criteria": <int>,
  "strong_chunk_score_threshold": <int>,
  "min_strong_chunks_for_keep": <int>
}}

RULES:

1. **Domain taxonomy**: Generate 8-15 domain-specific category labels that could be assigned to text chunks. These should be fine-grained enough to be useful for filtering but broad enough to cover the application scope. Use snake_case.

2. **Representative queries**: Generate queries that a user of this RAG application would actually ask. Scale the count to application scope:
   - Narrow, focused application: 12-15 queries
   - Moderate scope: 15-22 queries
   - Broad, multi-faceted application: 22-30 queries
   Each query must test a DISTINCT information need. No paraphrases. No duplicates.

   DERIVING QUERIES FROM KNOWLEDGE AXES:
   Read each knowledge axis description carefully. The description contains the specific materials, properties, decisions, and trade-offs that axis covers. Your queries MUST probe those specifics — do not generate generic questions that ignore the axis descriptions. For each PRIMARY axis, generate enough queries to cover ALL key aspects mentioned in its description. If an axis description mentions specific design variables (e.g., choosing between material grades, selecting additive types), at least one query must directly target that design variable.

   NO NUMBERS RULE (MANDATORY — zero tolerance):
   Do NOT embed ANY specific numbers in queries — no thresholds (e.g., ">30 MPa"), no percentages (e.g., "beyond 30 wt%", "more than 25%"), no fixed ranges (e.g., "between 10-20%"), no counts. Instead ask about general relationships, trends, and trade-offs (e.g., "What ratios optimize yield strength alongside impact resistance?" or "How does impact resistance change as LLDPE fraction increases?"). Numeric specifics cause papers with relevant data at other values to score zero utility.
   SELF-CHECK: Before finalising, scan every query. If any query contains a digit (0-9) or a number word (e.g., "thirty"), rewrite it to remove the numeric constraint.

   QUERY MATCHABILITY RULES (MANDATORY — these prevent low utility scores):

   a) BROAD MATERIAL SCOPE: Queries must use the general material class (e.g., "polypropylene blends") rather than a hyper-specific material system (e.g., "virgin impact copolymer versus virgin homopolymer in a three-component blend"). A paper studying the same material class with rich data but a slightly different formulation must still be able to score >= 3. Over-specifying the material combination in the query text causes the utility simulator to reject papers that study the right phenomena with the right data but use different component names or grades.

   b) SINGLE INFORMATION NEED PER QUERY: Each query must probe exactly ONE information need. Do NOT stack multiple conditions (e.g., "How does stabiliser X affect long-term tensile strength in blends with high recycled content?" combines stabilisers + long-term testing + recycled content — only papers covering ALL three will score well). If a compound question is important, split it into separate queries.

   c) PAPER-ANSWERABLE CONTENT ONLY: Queries must ask for information that research papers actually contain — experimental data, measured trends, material characterisation, processing parameters, formulation effects. Do NOT generate queries about industry standards, regulatory requirements, environmental certifications, or policy frameworks — these are almost never reported in scientific papers and will produce zero utility across the entire corpus.

   d) QUERY DIVERSITY CHECK: After drafting all queries, verify that no two queries are paraphrases of each other. Two queries that both ask "how does composition affect [property]?" with only the property name changed are near-duplicates. Merge or replace them. Aim for each query to probe a genuinely distinct facet: different independent variables, different phenomena, different data types (e.g., tables vs models vs morphology data).

   SELF-CHECK: Before finalising, for each query ask: "Could a solid experimental paper on this topic score >= 3 even if it studies a slightly different material grade or formulation than the application's primary system?" If the answer is no, broaden the query.

   PRIORITY WEIGHTING (MANDATORY — count and verify):
   Knowledge axes have a "priority" field (primary, secondary, supporting). Distribute queries as follows:
   - PRIMARY axes: at least 60% of total queries
   - SECONDARY axes: 25-30% of total queries
   - SUPPORTING axes: at most 10-15% of total queries
   SELF-CHECK: Before finalising, count the queries per priority tier. If the distribution violates these ratios, move queries from over-represented tiers to under-represented ones.
   If multiple primary axes exist, at least 3 queries should explore their INTERACTIONS (e.g., how a core property is affected by a core additive strategy) rather than treating each axis independently.

3. **Value criteria**: Generate 3-6 criteria that measure what makes content valuable FOR THIS APPLICATION. Each criterion must have concrete scale anchors that describe what each score level (0-5) means specifically for this application. Common criteria include actionability, specificity, quantitative density — but adapt them to the application. Derive criteria from the knowledge axes: primary axes should drive the main criteria, not supporting axes.

4. **Anti-patterns**: List 5-10 content types that should NOT be in the corpus. These are content types that may appear topically related but would add noise to the RAG system. Be precise: a paper that studies additives/fillers BUT also reports baseline binary blend data should NOT be excluded — only exclude papers that lack any relevant baseline data entirely.

5. **Evidence gate thresholds** (use these defaults — overly strict thresholds cause useful papers to be discarded):
   - strong_chunk_min_criteria: 2
   - strong_chunk_score_threshold: 3
   - min_strong_chunks_for_keep: 1

Output ONLY the JSON object. No explanatory text before or after.
